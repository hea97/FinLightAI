# FinLightAI 전시 피드백 및 제품 방향 분석

작성일: 2026-07-13
범위: 전시 피드백 정리, 현재 구현 상태 분석, 제품 방향과 로드맵 제안
작업 원칙: 이 문서는 분석 문서이며 frontend/backend/DB/기존 기획 문서는 수정하지 않는다.

## 1. 전시 결과 요약

FinLightAI는 전시에서 "뉴스 신뢰도와 시장 반응을 함께 보여주는 금융 정보 모니터링 대시보드"로 소개되었다. 관람자는 기능 수보다 데이터가 실제인지, 신뢰도 점수가 무엇을 뜻하는지, 포트폴리오와 로그인의 관계가 어떻게 설계되는지, 그리고 이 프로젝트가 실제 서비스로 배포될 수 있는지를 더 많이 질문했다.

가장 많이 질문된 영역은 인증과 배포, 데이터 표시 정확성, 뉴스 원문과 환율 같은 근거 데이터, 포트폴리오와 메모의 실제 사용 가치였다. 단순 오류와 제품 방향 질문은 구분해야 한다. `평균 신뢰도 72.00 / 1.00`, 동작하지 않는 빠른 필터, 의미 없는 별점, 원문 링크 부재, 설정 레이아웃 불균형은 즉시 수정 가능한 결함이다. 반면 로그인 유지 여부, 포트폴리오 저장 방식, 웹 서비스와 설치형 프로그램 중 무엇이 맞는지, 누가 돈을 내고 쓸 것인지는 제품 구조를 다시 정해야 하는 질문이다.

핵심 결론: FinLightAI는 기능을 더 붙이기보다 "공개 분석 화면"과 "개인화 저장 기능"의 경계를 다시 설계해야 한다. 공개 화면은 로그인 없이도 뉴스 신뢰도, 시장 신호, 산업 영향을 확인하게 하고, 로그인 또는 로컬 저장은 관심 자산, 시장 메모, 알림처럼 개인화가 필요한 기능에만 붙이는 방향이 적합하다.

## 3. 현재 프로젝트 구조와 구현 상태

### 제품 문서 기준

현재 문서는 FinLightAI를 투자 추천 서비스가 아니라 시장 상태와 근거를 제공하는 정보 서비스로 정의한다. `README.md`, `docs/CURRENT_DIRECTION_AND_GOALS_KO.md`, `docs/PRODUCT_PLANNING_KO.md`, `docs/SRS.md`는 공통적으로 다음 상태를 말한다.

- Google OAuth login/callback/me/logout 코드는 구현되어 있으나 Google Cloud Console, Render, Vercel 운영 설정은 미완료다.
- 전시 인증은 환경변수로 제한되는 `POST /api/auth/demo` 데모 로그인이다.
- 포트폴리오, 마이페이지, 설정, 이메일 구독은 사용자별 DB 저장 구조다.
- 이메일은 전시 MVP의 유일한 알림 채널이며 Resend/SMTP provider 설정과 production smoke test가 필요하다.
- 카카오/n8n은 전시 범위에서 제외되어야 한다.
- provider/fallback/warning metadata와 운영 상태 API는 실제 데이터 안정성을 보여주기 위한 구조다.

### Frontend 기준

- `frontend/src/App.tsx`는 대부분의 화면을 단일 파일 안에 포함한다. AI 브리핑, 뉴스 가드, 산업 영향도, 포트폴리오, 마이페이지, 설정, 로그인/공개 페이지가 한 곳에 있어 빠른 전시 구현에는 유리하지만 제품화 단계에서는 화면 단위 분리가 필요하다.
- `NewsGuardKpiGrid`는 평균 신뢰도 표시를 `stats.averageReliabilityScore.toFixed(2)`와 `/ 1.00`으로 고정한다. 전시 데이터가 72 스케일일 때 표시 오류가 발생한다.
- `NewsGuardArticleCard`는 `originalUrl ?? "#"`로 링크를 만든다. URL 없는 기사는 실제 링크처럼 보일 수 있다.
- `stars(score)`는 0~1 점수 전제의 별점 함수다. 0~100 점수와 섞이면 모든 별점이 채워질 수 있다.
- `NewsFilterTabs`는 `all/trusted/watch/blocked` API 필터와 연결되어 있지만, quick filter 항목은 별도 상호작용 상태가 약하다. `최신순`, `필터` 버튼은 실제 동작이 없다.
- `DEMO_STORAGE_KEYS`와 localStorage helper가 있어 전시 모드의 portfolio/settings 저장은 브라우저 저장으로 가능하다. 다만 일반 비로그인 포트폴리오 저장 정책으로 정리되어 있지는 않다.
- `toKrw()`에 KRW/USD/TWD 환율이 하드코딩되어 있지만, 환율 카드와 provider 출처 표시는 없다.

### Backend 기준

- `src/dashboard/routes/api.py`는 `/api/auth/google/login`, `/api/auth/google/callback`, `/api/auth/demo`, `/api/auth/me`, `/api/auth/logout`를 제공한다.
- `_current_user_id`는 production에서는 session cookie를 우선하고, 개발 환경에서는 `X-User-ID` fallback을 허용한다. 문서 정책과 일치한다.
- `/api/portfolio`, `/api/mypage`, `/api/settings`, `/api/email-subscription`, `/api/notifications/dispatch`, `/api/notifications/email-events`가 구현되어 있다.
- `src/dashboard/models.py`에는 users, portfolio_assets, user_settings, email_subscriptions, notification_deliveries 등 운영 저장 모델이 있다.
- `src/notifier/notification_service.py`는 이메일 double opt-in, unsubscribe, dispatch, provider webhook 상태 반영 구조를 갖는다.
- 카카오/n8n 관련 레거시 설정과 route 일부는 남아 있지만 문서상 전시 노출 제외다. 제품화 전에는 제거 또는 명확한 비노출 처리가 필요하다.

### 배포 및 테스트 기준

- README는 로컬 실행, Docker, Vercel frontend, Render backend, PostgreSQL 운영 구조를 설명한다.
- 최신 문서 기준으로 2026-07-09 backend test 78개, 알림 지정 테스트 12개, frontend production build 통과 기록이 있다.
- 실제 운영 URL, Google OAuth redirect, CORS, secure cookie, 이메일 provider 도메인, PostgreSQL migration, refresh scheduler, production smoke test는 남은 작업이다.

## 4. 로그인 필요성 분석

### 현재 로그인 기능은 어떤 데이터 때문에 필요한가?

현재 서버 로그인은 사용자별 데이터 분리를 위해 필요하다. 포트폴리오 자산, 마이페이지 관심 산업, 설정, 온보딩 preference, 이메일 구독, 알림 발송 이력은 사용자 ID에 귀속된다. 여러 기기에서 같은 데이터를 보거나 이메일 알림을 운영하려면 서버 계정이 필요하다.

반대로 AI 브리핑, 뉴스 가드, 산업 영향도 같은 공개 분석 화면은 개인 데이터를 요구하지 않는다. 이 화면은 로그인 없이도 제공할 수 있다. 로그인 장벽을 낮추는 것이 전시 피드백과 상품화 모두에 유리하다.

### 서버 계정이 실제로 필요한 기능

- 이메일 구독, double opt-in, 수신 거부, bounce/complaint 관리
- 여러 기기에서 같은 포트폴리오와 설정 동기화
- 사용자별 알림 규칙과 dispatch 이력
- 개인화 리포트, 관심 종목 기반 요약, 장기 기록 백업
- 개인정보 삭제 요청, 운영 감사, abuse 방지

### 로그인 없이 localStorage만으로 가능한 기능

- 단일 브라우저의 관심 종목 목록
- 간단한 포트폴리오 입력과 평가금액 계산
- 표시 설정, 뉴스 필터 선호도
- 시장 메모 초안 저장
- export/import 파일을 통한 백업과 이동

### localStorage 방식의 장점과 한계

장점은 진입 장벽이 낮고, 전시장에서 로그인 실패 리스크가 작으며, 개인정보 부담도 줄어든다는 점이다. 사용자는 바로 포트폴리오와 메모를 써볼 수 있다.

한계는 브라우저/기기마다 데이터가 분리되고, 삭제나 캐시 초기화로 데이터가 사라질 수 있으며, 이메일 알림과 서버 기반 분석 이력에는 연결하기 어렵다는 점이다. 따라서 localStorage는 "비로그인 체험과 개인 임시 저장"에는 적합하지만, 운영형 개인화 서비스의 최종 저장소로는 부족하다.

### 선택 로그인 방식

권장 모델은 선택 로그인이다.

```text
비로그인 사용자
-> 공개 브리핑/뉴스 가드/산업 영향도 조회
-> localStorage 포트폴리오/시장 메모 작성
-> export/import로 백업
-> 이메일 알림, 여러 기기 동기화, 장기 기록이 필요할 때 Google OAuth
-> 서버 DB로 동기화
```

이 방식은 전시 피드백의 "로그인이 정말 필요한가?"라는 질문에 답하면서도, 이메일 알림과 장기 개인화 기능을 포기하지 않는다.

### 이메일 알림은 로그인까지 필요한가?

이메일 알림은 두 단계로 나눌 수 있다. 단순 뉴스레터 구독은 이메일 주소와 double opt-in만으로도 가능하다. 하지만 사용자별 포트폴리오와 관심 산업에 맞춘 알림, 알림 이력, suppression, 설정 관리는 계정 또는 최소한의 subscriber identity가 필요하다. 따라서 초기에는 "이메일만으로 구독"을 허용하고, 개인화 알림은 로그인 사용자에게 제공하는 구조가 현실적이다.

### 전시 데모와 실제 제품 인증 정책

전시 데모는 shared demo account라서 관람자가 빠르게 체험하는 데 적합했다. 실제 제품에서는 공유 계정이 개인정보와 데이터 혼선 문제를 만든다. 전시용 데모 로그인은 운영 제품에서 제거하거나 sandbox 체험으로 격리하고, 실제 저장/알림은 선택 Google OAuth 또는 이메일 기반 계정으로 전환해야 한다.

## 5. 로그인 모델 비교

| 모델 | 구조 | 장점 | 단점 | 개발 비용 | 운영 비용 | 개인정보 부담 | 적합한 사용자 |
|---|---|---|---|---|---|---|---|
| 모델 A. 로그인 필수 | 사용자 로그인 -> 서버 DB -> 포트폴리오/메모/설정 동기화 | 데이터 일관성, 알림 운영, 여러 기기 동기화가 좋다. | 첫 진입 장벽이 높고 OAuth 설정 실패 시 핵심 화면까지 막힐 수 있다. | 높음 | 높음 | 높음 | 장기 사용자, 알림/리포트를 원하는 사용자 |

| 모델 C. 선택 로그인 | 공개 대시보드 + localStorage 기본 저장 + 로그인 시 서버 동기화 | 진입 장벽과 제품화 가능성을 모두 잡는다. | 동기화 정책, 충돌 처리, export/import 설계가 필요하다. | 중간~높음 | 중간 | 중간 | 개인 투자 학습자, 관심 종목 추적 사용자 |

권장 방향은 모델 C다. FinLightAI의 핵심 분석 화면은 공개로 열고, 저장·동기화·알림·사후검증은 로그인 사용자의 프리미엄 경험으로 만든다.

## 6. 목표 사용자와 유료 가치

### 사용자군 1. AI·반도체 종목에 관심 있는 개인 투자자

- 반복 문제: 뉴스는 많지만 어떤 뉴스가 내 관심 종목에 실제로 중요한지 구분하기 어렵다.
- 현재 대안: 증권 앱 뉴스, 포털 검색, 커뮤니티, 유튜브 요약.
- FinLightAI 가치: 뉴스 신뢰도와 시장 반응을 함께 보여주고, 포트폴리오 기준으로 노출도를 정리한다.
- 지불 가능 기능: 관심 종목별 RED/YELLOW 알림, 뉴스 신뢰도 판단 사유, 예상/실제 반응 비교 기록.
- 필요한 근거: 원문 URL, provider 상태, 가격/거래량/환율 출처, 신호 산식 설명.
- 추천 표현: `매수/매도`가 아니라 `관심 종목에 연결된 검증 필요 이벤트`로 표현한다.

### 사용자군 2. 금융 뉴스를 많이 읽지만 정리하기 어려운 초보 사용자

- 반복 문제: 뉴스 용어와 시장 영향이 어려워 매일 읽어도 정리가 남지 않는다.
- 현재 대안: 뉴스레터, 증권사 리포트, 요약 앱.
- FinLightAI 가치: 아침 시장 요약, 신뢰도 높은 기사 우선순위, 쉬운 색상 신호.
- 지불 가능 기능: 매일 아침 요약, 쉬운 판단 사유, 관심 산업별 핵심 이벤트.
- 필요한 근거: 쉬운 해설, 용어 설명, 실제 원문 연결.
- 추천 표현: `투자 판단`보다 `시장 이해를 돕는 학습형 브리핑`으로 표현한다.

### 사용자군 3. 특정 산업과 기업을 모니터링하는 분석가 또는 실무자

- 반복 문제: 특정 기업/정책/발언이 산업 분위기에 미친 영향을 기록하고 나중에 검증해야 한다.
- 현재 대안: 노션, 스프레드시트, 사내 리포트, 검색 알림.
- FinLightAI 가치: 출처 있는 발언, 이벤트, 시장 반응, 후속 결과를 한 기록으로 묶는다.
- 지불 가능 기능: 팀 공유, 리포트 export, 발언 추적, 과거 유사 이벤트 검색.
- 필요한 근거: 출처 URL, 발언자, 신뢰 수준, 영향 방향, 실제 반응 데이터.
- 추천 표현: `주가 예측`이 아니라 `시장 이벤트 관찰 기록과 사후검증`으로 표현한다.

1차 목표 사용자는 사용자군 1이다. 이유는 현재 코드의 포트폴리오, 뉴스 가드, 산업 영향도, 이메일 알림이 이 사용자에게 가장 가깝고, B2B SaaS보다 개발·운영 범위가 작기 때문이다. 사용자군 3은 확장 방향으로 적합하지만, 지금 바로 주 방향으로 삼기에는 팀 기능, 권한, 리포트, 데이터 비용이 크다.

## 8. 시장 메모 기능 구체화

권장 이름은 `시장 메모`다. `개인 메모`보다 금융 이벤트와 사후검증 성격이 분명하고, `투자 일지`보다 투자 추천 오해가 적다. 대안 이름은 `시장 관찰 기록`, `이벤트 노트`, `뉴스 반응 기록`이다.

### 데이터 구조 제안

| 필드 | 설명 |
|---|---|
| id | 메모 고유 ID |
| ticker | 연결 종목 코드 |
| companyName | 기업명 |
| title | 메모 제목 |
| content | 사용자의 해석 또는 관찰 |
| memoType | 생각, 뉴스, 발언, 정책, 실적, 리스크 |
| sourceType | 뉴스, 공시, 인터뷰, 컨퍼런스콜, 리포트, 직접 입력 |
| sourceName | 매체명, 기관명, 발언 장소 |
| sourceUrl | 원문 URL |
| speaker | 발언자 |
| statement | 핵심 발언 |
| confidenceLevel | 높음, 보통, 낮음, 확인 필요 |
| expectedDirection | 긍정, 부정, 중립, 변동성 확대, 판단 보류 |
| expectedPeriod | 당일, 1주, 1개월, 장기 |
| createdAt | 작성 시각 |
| reviewDate | 사후 검토 예정일 |
| actualReturn | 검토 시점 실제 수익률 또는 가격 변화 |
| resultNote | 예상과 실제 차이 기록 |
| tags | 산업, 이슈, 정책, 기업 태그 |
| emailAlert | 검토일 또는 관련 뉴스 발생 시 이메일 알림 여부 |

### 예시 흐름

```text
삼성전자 관련 뉴스 확인
-> "임원 발언" 유형으로 시장 메모 작성
-> sourceUrl과 speaker 기록
-> expectedDirection = 긍정, expectedPeriod = 1주
-> 1주 뒤 actualReturn과 관련 뉴스 변화 자동 표시
-> 사용자가 resultNote에 예상이 맞았는지 기록
```

이 기능은 FinLightAI를 단순 뉴스 대시보드에서 "근거 있는 시장 관찰과 사후검증 도구"로 바꾼다.

## 9. 제품 방향 후보 비교

### 방향 1. 개인 투자자용 뉴스 리스크 대시보드

- 특징: 현재 코드와 가장 가깝다. 공개 브리핑, 뉴스 가드, 산업 영향도, 포트폴리오, 이메일 알림을 유지한다.
- 현재 코드 재사용 가능성: 높음.
- 완성까지 기간: 2~4주.
- 데이터 비용: 낮음~중간.
- 사용자 가치: 관심 종목의 뉴스 리스크를 빠르게 파악한다.
- 포트폴리오 평가 가치: 높음.
- 상품화 가능성: 중간~높음.
- 운영 난이도: 중간.

### 방향 2. 투자 학습·리서치 노트

- 특징: 시장 메모, 출처 있는 발언, 예상/실제 반응 비교, 학습 기록을 중심으로 한다.
- 현재 코드 재사용 가능성: 중간. 포트폴리오와 뉴스 가드는 재사용 가능하지만 새 데이터 모델이 필요하다.
- 완성까지 기간: 4~8주.
- 데이터 비용: 중간.
- 사용자 가치: 사용자가 자신의 판단을 개선하는 데 직접 도움이 된다.
- 포트폴리오 평가 가치: 중간.
- 상품화 가능성: 높음.
- 운영 난이도: 중간~높음.

### 방향 3. 산업 이벤트 모니터링 SaaS

- 특징: 기업 또는 분석 실무자 대상, 특정 산업/기업/정책 추적, 팀 공유, 리포트와 알림 중심.
- 현재 코드 재사용 가능성: 중간.
- 완성까지 기간: 2~3개월 이상.
- 데이터 비용: 높음.
- 사용자 가치: 팀 단위 모니터링과 리포트 자동화.
- 포트폴리오 평가 가치: 낮음~중간.
- 상품화 가능성: 높지만 영업/데이터/권한 기능이 필요하다.
- 운영 난이도: 높음.

최종 권장 주 방향은 방향 1이다. 현재 코드와 문서가 이미 이 방향에 맞춰져 있고, 전시 피드백의 대부분도 이 방향을 더 안정적으로 만들라는 신호다. 계속 확장할 방향은 방향 2다. 시장 메모와 사후검증 기능을 붙이면 방향 1의 대시보드가 방향 2의 학습·리서치 노트로 자연스럽게 깊어진다. 방향 3은 장기 후보로 남긴다.

## 11. 최종 의사결정

1. 로그인은 유지하되 필수로 두지 않는다. 공개 분석 화면은 비로그인으로 열고, 서버 저장·여러 기기 동기화·이메일 개인화 알림에만 로그인을 요구한다.
2. 로그인 없이 포트폴리오는 localStorage에 저장한다. 이후 사용자가 로그인하면 서버 DB로 가져오기 또는 병합하는 흐름을 제공한다.
3. FinLightAI는 설치형 프로그램보다 웹 서비스가 적합하다. GitHub 로컬 실행은 개발자와 전시 백업용으로 유지한다.
4. 핵심 사용자는 AI·반도체·정책 뉴스가 관심 종목에 미치는 영향을 추적하는 개인 투자 학습자다.
5. 사용자가 돈을 지불할 핵심 가치는 단순 뉴스 요약이 아니라 관심 종목 이벤트의 신뢰도, 시장 영향, 나의 기록, 실제 반응을 함께 남기는 기능이다.
6. 가장 먼저 고칠 세 가지는 신뢰도 단위, 별점 제거, 빠른 필터/원문 링크처럼 클릭 가능한 요소의 실제 동작이다.
7. 전시용 프로젝트에서 실제 서비스로 전환하려면 production 배포, provider 상태 표시, 데이터 refresh 스케줄, 이메일 provider 검증, 선택 로그인 정책이 부족하다.
8. 과감히 제거해도 되는 기능은 의미 없는 별점, 동작 없는 버튼, 운영 준비 전 카카오/n8n 노출, 전시 데모를 실제 계정처럼 보이게 하는 표현이다.
9. 앞으로 추가해야 할 대표 기능 한 가지는 시장 메모다. 단, 단순 텍스트 메모가 아니라 출처·발언·신뢰 수준·예상과 실제 반응 비교를 포함해야 한다.
10. FinLightAI를 한 문장으로 다시 정의하면: FinLightAI는 관심 종목에 연결된 뉴스의 신뢰도와 시장 반응을 추적하고, 사용자의 관찰 기록과 사후검증까지 돕는 금융 정보 모니터링 서비스다.

## 13. 전시 효과와 운영 제품의 구분

전시에서는 기능의 존재와 아이디어 전달이 중요했다. 운영 제품에서는 데이터의 출처, 점수 단위, 링크 동작, 저장 위치, 개인정보 경계가 더 중요하다. 따라서 전시용 demo mode는 유지하되, 실제 서비스 화면에서는 다음 네 가지를 반드시 분리해야 한다.

- 전시 데모 데이터와 실제 provider 데이터
- 공개 조회 기능과 개인화 저장 기능
- 브라우저 localStorage 저장과 서버 DB 저장
- 알림 구현 코드와 실제 provider 운영 검증

이 구분이 선명해지면 로그인 제거 여부 같은 질문도 더 쉽게 답할 수 있다. "로그인은 분석을 보기 위한 문이 아니라, 내 기록과 알림을 오래 보관하기 위한 선택 기능"이라고 설명하면 된다.
